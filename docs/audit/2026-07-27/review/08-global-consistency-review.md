审计日期：2026-07-27

## 1. 复核结论

本次复核只检查 `docs/audit/2026-07-27/00-repository-map.md` 至
`17-independent-full-sweep.md` 的报告质量与跨报告一致性，不重新执行完整代码审计，也不修改
原报告或应用代码。

18 份报告中，00 号是仓库地图，其余 17 份共包含 247 个带编号标题。这个数字不能作为独立问题
总数：其中既包含已确认缺陷，也包含风险、假设、待产品决策项、提示项和同一根因的重复观察。
跨报告至少存在 35 组明确重复或高度重叠的问题簇，13、17 号报告内部还存在可避免的重复计数或
复用编号。

总体判断如下：

- 大多数正式发现都给出了可定位的文件、行号和因果链，证据质量明显高于纯清单式审计。
- 后端全量测试、前端测试、SDK 测试、构建、静态检查和浏览器验证的结果总体可以互相解释，
  但必须保留命令、环境和验证边界，不能压缩成“测试全绿”或“测试失败”一句话。
- 严重度不可直接横向汇总。各报告分别使用“严重/高/中/低”“P0—P3”“中等/较低”和
  “提示”，且相同问题被评为中、高、严重或 P0。
- 已确认事实、源码可达风险、条件性平台风险、产品决策项和待验证假设总体有分区，但仍有少数
  结论被提升过早，尤其是占位功能、浏览器兼容范围、公开部署可达性和性能实际影响。
- 修复建议多数符合项目“正本清源、快速失败、不保留兼容层”的硬约束；需要纠正的主要是
  未知枚举兜底、全局错误兜底、泛化成功 Toast，以及在未先确定支持边界时增加平台兼容分支。

最终总综述应按“根因簇”计数和排序，所有引用使用“报告号/发现编号”，例如
`[06]/C-01`，不能只写 `C-01`。

## 2. 复核方法与证据边界

本次完成了以下检查：

1. 逐份读取 00—17 号报告的范围、结论、发现标题、严重度、置信度、验证记录、修复顺序和边界说明。
2. 提取 247 个编号标题，检查编号碰撞、层级、确认/风险/假设分类和报告内计数。
3. 按代码位置、触发路径、根因和修复目标建立跨报告去重簇，而不是只按标题相似度匹配。
4. 对冲突点抽查当前基线源码和配置：
   - 当前提交为 `18cd9363854efd9dfb0dce82291543c43b517add`，分支为 `main`；
   - `frontend/package.json` 的 `test` 确实是 `node -e`、`spawnSync` 和
     `shell: true` 的包装器，不是简单参数透传；
   - `docker-compose.deploy.yml` 自称公网反代部署，写有公网域名、`DEBUG=1`、
     `runserver`、SQLite 和本地镜像，但本次没有验证该域名当前是否从互联网可达；
   - 当前 `db.sqlite3` 权限确为 `0644`，`.env.local` 权限为 `0600`。
5. 未重新运行完整测试、构建、浏览器套件或外部网络探测。命令结果一致性判断以原报告记录和上述
   最小抽查为准。

只有 00、13、14 号报告在正文中明确写出完整或缩写提交基线。其他报告虽然引用的文件形态与当前
提交一致，但最终归档最好统一补充提交 SHA、命令时间和关键工具版本；否则将来无法严格区分
“同一代码、不同环境”与“报告期间代码变化”。

## 3. 结构、编号和严重度审查

### 3.1 编号不是全局唯一

以下编号发生跨报告碰撞：

| 编号范围 | 报告 | 问题 |
| --- | --- | --- |
| `C-01`—`C-13` | 06、17 | 同一编号表示完全不同的问题；17 号又重复了 06 号的若干结论，但编号没有继承关系 |
| `R-01`—`R-05` | 06、13 | 06 号表示前端条件风险，13 号表示死代码/兼容契约风险 |
| `H-01`—`H-02` | 05、17 | 05 号是前端架构假设，17 号是路由与 Toast 布局假设 |

01 号的 `HYP-*`、02 号的 `BF-*`/`BR-*` 等前缀较清楚；17 号再次使用通用 `C-*` 是最明显的
全局可追踪性问题。原报告不需要回改，但总综述必须始终带报告号。

03 号把每个发现写成二级标题，其他报告通常使用三级标题。这不会改变内容，但会让自动目录把
单项发现与“范围”“建议顺序”等章节置于同级。后续统一模板宜规定：报告章节用二级标题，发现
用三级标题。

13 号存在报告内重复：`D-02` 已列出 `paginate_items` 和
`expiring_grant_items_for_user` 两个无调用函数，`D-05` 又把同两个函数计入“4 个后端函数
没有调用方”。总综述不得把它们计算两次。

### 3.2 严重度口径不可直接换算

相同事实在不同报告中的评级示例：

| 根因 | 评级差异 |
| --- | --- |
| 应用启停/删除失败无反馈 | `[06]/C-02` 为中；`[09]/TF-03`、`TF-04` 为高；`[17]/C-02` 为严重 |
| 列表契约错误降级为空列表 | `[06]/R-01` 为中；`[12]/F-02`、`[15]/CTR-04` 为高；`[17]/C-01` 为严重 |
| 原始校验/异常细节进入 UI | `[08]/I18N-04`、`I18N-10` 使用 P0；`[16]/SPB-06` 为中 |
| Dialog/Toast 无进退场动效 | `[10]/MOT-02` 为中、`MOT-05` 为低；`[17]/C-13` 统一为较低 |

这些差异主要来自各报告的局部尺度，不表示事实矛盾。最终总综述应重新评级，而不是把 `P0`
机械映射为“严重”，或选取重复报告中的最高等级。

建议总综述只使用四级统一口径：

- 阻断：已确认破坏信任根、系统级撤权或不可自动恢复的关键安全/交付动作。
- 高：已确认造成权限/业务事实错误、核心流程假成功或数据契约被掩盖。
- 中：可恢复的功能失效、明显用户误导、有限信息暴露或确定的工程门禁缺口。
- 低：维护性、体验、容量条件或尚需产品口径决定的问题。

性能项应把“源码确认存在无界/N+1/锁内网络调用”与“生产已发生延迟或资源耗尽”分开；没有压测
或生产指标时，后者不能写成已发生事实。

### 3.3 建议统一验证状态

原报告混用“已验证”“已确认”“代码推断”“条件性风险”“风险项”“待验证假设”和
“需要外部契约确认”。最终总综述建议采用以下状态：

| 状态 | 含义 |
| --- | --- |
| `动态验证` | 已用命令、最小复现、数据库只读探针或浏览器行为实际验证 |
| `静态验证` | 从当前代码可确定到达错误状态，不依赖未定义外部行为 |
| `条件成立` | 代码失效路径存在，但取决于数据规模、浏览器基线、外部响应或部署拓扑 |
| `待决策` | 是否为缺陷取决于尚未确认的产品、安全或外部契约 |
| `假设` | 只有风险结构，尚未证明可达或真实影响 |

“置信度高”不能替代上述状态。例如某个未使用公开 SDK 符号在仓库内零引用的置信度可以很高，
但是否有外部消费者仍是`待决策`。

## 6. 事实冲突与裁决

### 6.1 前端全量测试失败数不是稳定事实

报告记录了三种结果：

- `[06]`：首次默认并行运行出现 10 个超时失败，单 worker 全量通过；
- `[12]`：一次完整运行 11 项失败，紧接着另一次完整运行 295 项全过；
- `[17]`：一次运行 10 项失败，拆分单 worker 重跑通过；
- `[14]`：在临时归档目录中 295 项全过。

这些结果共同证明“门禁结果不可重复”，不证明固定存在 10 或 11 个失败，也不足以把具体根因
确认成“并发竞争”。`[12]/F-01` 正确地把现象置信度写为高、具体根因写为中；总综述应采用
该口径。应排除固定失败数和“已确认并发根因”的表述。

### 6.2 17 号对测试脚本的描述与源码冲突

`[17]/C-08` 称 `frontend/package.json:10` “只是把参数透传给 Vitest”。实际脚本是
`node -e` 调用 `spawnSync('vitest', args, { shell: true })` 的包装器；`[05]/EA-FE-09`
和 `[14]/BCO-11` 已实际复现不同参数形式的失败。

裁决：保留“测试脚本参数转发有缺陷”，排除 17 号“只是参数透传”的证据描述。这个错误不推翻
Vitest 非确定性现象，但说明 17 号的根因分析不能单独采用。

### 6.3 Playwright 的“27 项失败”不是业务测试失败

`[12]` 已说明 27 项全部停在 Chromium Headless Shell 不存在，业务断言未执行；`[07]`
后来使用本机 Chrome 完成了部分隔离布局验证。二者不矛盾。

裁决：总综述应写“默认 Playwright 环境不可直接运行；现有隔离浏览器套件不验证真实后端”，
不得写“27 个 E2E 场景验证失败”。

### 6.4 “公网部署”与“互联网可达”不是同一事实

14、16 号以 `docker-compose.deploy.yml` 的首行注释、域名、CSRF origin、frpc 注释和
运行配置证明仓库内存在一条自称“公网反代部署”的开发级路径。这足以确认配置危险，但没有网络
探测、DNS、反代状态或流量证据证明该服务当前从互联网可达。

裁决：配置缺陷保持高优先级；“当前公网正在暴露”“外部攻击者现在可访问”必须排除或加
“若该编排实际启用并暴露”的条件。

### 6.5 PostgreSQL 是规范基线，SQLite 是当前部署分叉

00 号称“生产基线 PostgreSQL”，指 `README`、架构和基础设置的规范口径；14、16 号确认
当前仓库中的反代编排强制 SQLite。两者不是数据库检测结果冲突，而是规范与实际部署分叉。

裁决：总综述不能简单写“生产使用 PostgreSQL”，也不能把本地/反代 SQLite 泛化为所有环境；
应明确记录这条部署分叉本身就是问题。

### 6.6 浏览器动态验证范围不同

07 号在 `localhost:8001` 验证了未登录认证模板，并用 Vite/API 隔离数据渲染受保护 React
页面；10 号访问的是 `127.0.0.1:8000`，且明确未完成可信交互实测。二者不矛盾。

裁决：07 号的布局截图可作为真实浏览器渲染证据，但不能证明真实鉴权或数据链；10 号动效项仍为
源码推断，不得借用 07 号的浏览器验证升级。

### 6.7 后端测试通过与质量门禁失败可以同时成立

02、11、14、17 号均记录主后端套件 `1291 passed, 1 skipped`。14 号同时记录 Ruff 15 项、
BasedPyright 1718 项错误；11 号说明 SDK 需要正确 `PYTHONPATH`，FastAPI 模块仍跳过，
PostgreSQL 并发用例在 SQLite 默认套件中跳过。

裁决：总综述可以说“主后端 SQLite 套件在该基线通过”，不能说“全仓质量门禁通过”或
“后端正确性已验证”。

### 6.8 未知枚举的两个修复建议不兼容

`[08]/I18N-06` 建议未知状态在 UI 显示“未知状态/暂不支持的状态”；`[15]/CTR-07` 要求
封闭枚举、未知值触发契约错误。若把未知值作为正常行状态渲染，仍是在用显示兜底掩盖契约漂移。

裁决：采用 15 号口径。解析层必须快速失败并进入明确的区块错误态；用户可见错误页可以显示
本地化的“数据状态暂不受支持”，但不能继续把该行当成合法业务状态渲染。

### 6.9 成功 Toast 建议需要收敛

`[17]/C-02`、`C-03` 倾向为启停、删除和多数管理写操作增加成功/失败 Toast；`[09]` 明确
指出列表消失、Badge 更新、对话框关闭或页内“已保存”有时已经是充分成功反馈，重复 Toast 会
增加噪声和读屏重复播报。

裁决：失败必须可见；成功反馈按动作风险和状态变化可见性选择 Toast、页内状态或界面变化。
不得把“每个 mutation 都弹成功 Toast”写入统一验收标准。

## 7. 证据质量与需要降格的结论

### 7.1 可以直接进入总综述的强证据

- 有最小动态复现或明确数据探针：`BF-01`、`BF-04`、`BF-05`、03 号数据库形状检查、
  11 号测试替身/跳过项、14 号构建与配置探针、16 号会话与 Pydantic 探针。
- 可由单一路径确定达到错误状态：锁内网络调用、非原子 `sign_count`、非法列表载荷返回
  空数组、剪贴板未等待、查询失败被隐藏、缺失撤回入口、分页只读第一页。
- 真实浏览器或隔离浏览器确认的布局与语义：07 号明确标注为浏览器验证的条目。

### 7.2 必须保持条件性的结论

- 04 号所有依赖数据量、并发量或外部响应规模的性能后果：机制已确认，实际容量影响未压测。
- 06 号 `R-02`—`R-04`：只有产品支持对应受限浏览器/WebView 时才是兼容性缺陷。
- 13 号公开 SDK/活跃 legacy 契约删除：仓库内零引用不等于外部消费者为零。
- 14、16 号公网可达性：配置意图明确，当前外部暴露状态未验证。
- 17 号 `C-09`：主包体积和无分包已确认，实际首屏性能影响未测量。
- 17 号 `C-10`：移动导航横向滚动结构已确认，是否阻断任务需真实设备任务测试。
- 10 号全部动效项：组件生命周期缺失已确认，用户影响为代码推断。

### 7.3 必须保留为产品或架构决策的结论

- `[02]/BR-01`：未绑定第二因子的本地管理员能否进入控制台是当前已记录设计，需要安全政策决定。
- `[02]/BR-02`：是否保留 Django Admin 取决于正式特权平面设计和部署暴露边界。
- `[02]/BR-04`：全部 App 基础目录是否对 Console 用户可见取决于产品最小披露要求。
- `[03]/DS-11`：授权版本究竟代表可变当前修订还是不可变历史快照，报告自身置信度为中。
- `[13]/R-04`：CRM seed 是产品入口还是开发样例尚未决定。
- `[17]/C-04`：占位入口只有在产品宣称可用、导航承诺功能或阻断既定流程时才能定为缺陷；
  单凭“组件存在且显示占位”不足以证明严重度。

## 8. 修复建议与项目硬约束的一致性

### 8.1 一致且应保留的原则

以下跨报告建议与项目硬约束高度一致：

- 删除列表空数组、连接器空配置、非法分页默认值和外部 DTO 宽松解析等静默兜底。
- 建立单一 schema/领域事实源，并一次性更新后端、前端、测试和中文文档。
- 删除未进入 legacy 白名单、没有外部契约和移除条件的兼容字段、别名和正向兼容测试。
- 对状态机、不变量、幂等和事务错误快速失败，不能把部分失败或依赖故障改写成成功。
- 在未上线前重建正确 schema，而不是为错误模型增加长期读取兼容层。

### 8.2 需要修正或加前置条件的建议

1. 未知枚举：不能以“未知状态”作为正常数据兜底；必须先让契约解析失败，再显示通用错误界面。
2. 全局 mutation 错误处理：`[09]/TF-22` 的全局钩子只能处理已明确标记且未消费的错误；
   新 mutation 缺少反馈策略应由类型、测试或 lint 直接失败，不能依赖全局 Toast 掩盖遗漏。
3. 成功反馈：不得把所有写操作统一成成功 Toast。错误必须可见，成功应按风险和界面是否已经
   明确变化选择单一反馈。
4. 浏览器兼容：对 `localStorage`、`ResizeObserver`、`crypto.randomUUID` 的 polyfill 或
   内存替代必须在明确支持矩阵后决定；不要为未定义平台长期增加投机兼容分支。
5. 密钥轮换：14、16 号建议的旧密钥解密—新密钥重加密属于一次性受控迁移，不是长期兼容；
   必须有前置检查、原子切换、验证和旧密钥销毁条件。
6. 迁移压平：项目未上线允许重建初始 schema，但当前本地试点库已有数据。若这些数据需要保留，
   必须走显式导出/迁移和人工确认；不能用“未上线”作为静默删除本地事实的理由。
7. 异步解耦：把同步连接器/Webhook 调用改为 outbox 后，必须同时落实租约恢复、幂等重投和
   watchdog；仅把调用移出事务而不建设恢复状态机会把同步失败变成异步静默丢失。
8. 用户错误文案：原始异常不能直接展示给用户，但也不能被吞掉；应保留稳定诊断编号、受控日志和
   结构化字段错误，UI 只展示可执行的本地化信息。

## 10. 建议的最终综合排序

去重并重新评级后，建议总综述按以下根因层级组织，而不是按 17 份专题报告顺序串联：

1. 部署与身份信任根：GC-30、GC-31、GC-01、GC-02，以及确认后的 Django Admin 边界。
2. 不可恢复或假成功的异步状态机：Webhook 悬空、离职禁号假成功、目录代次部分成功、
   通知对账假成功、交接复合状态。
3. 授权与数据不变量：申请基础版本、模板修订、状态机数据库约束、跨 App 归属、
   WebAuthn 计数和事件幂等。
4. 严格跨层契约：GC-06、GC-14、GC-15、GC-17、GC-20，以及四类申请和缓存失效矩阵。
5. 管理能力与用户反馈：GC-07—GC-13、GC-26、会话过期重认证和复合审批结果。
6. 质量门禁：GC-21—GC-25、GC-28，先消除假绿灯和不可复现入口，再删低价值测试。
7. 隐私、保留与最小披露：GC-19、GC-32、敏感浏览器状态和匿名运行状态暴露。
8. UI、国际化、无障碍、动效和包体：仅在保留动态/静态/条件性证据标签后排期。

每个规范根因项应只保留一个标题，在“来源”字段列出所有原报告编号；修复验收应覆盖 schema、
domain、API、frontend、tests 和中文文档，不建立双轨兼容期。
