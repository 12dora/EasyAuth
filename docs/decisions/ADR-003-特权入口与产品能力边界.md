# ADR-003：特权入口与产品能力边界

## 状态

已接受

## 日期

2026-07-27

## 背景

有五个安全与产品口径长期悬而未决：本地超级管理员是否可长期单因素、Django Admin 是否保留为平行特权面、全部 App 基础目录是否对所有控制台用户可见、授权版本语义按可变 `version` 还是不可变历史修订解释，以及通知中心和门户安全设置这类占位入口是否构成已承诺能力。

项目尚未上线，不保留错误设计的兼容形态；这些口径必须一次性落到 schema、domain、API、frontend、tests 和文档。

## 决策

1. 本地超级管理员必须绑定至少一种二次因子后才可形成控制台超级管理员 actor。密码验证后若账号没有 TOTP 或 Passkey，只允许进入本地安全设置页完成绑定；控制台 API 请求期若发现本地管理员没有任何二次因子，必须拒绝形成 `ConsoleActor`。
2. Django Admin 不作为 EasyAuth 产品特权入口。生产 URL 路由移除 `/admin/`，关键模型只能通过 EasyAuth 控制台 API 和同一套 actor、二次验证、会话撤权与审计边界操作。Django admin 类可以作为内部表单和只读约束测试对象存在，但不得被 URL 暴露。
3. App 基础目录不再对所有控制台登录用户全量可见。超级管理员可查看全部 App；普通控制台用户只能查看自己 active owner/developer 成员关系覆盖的 App。详情、配置和写操作继续使用同一成员关系与超级管理员规则。
4. 授权版本以当前已引入的 `AccessGrant.version`/`base_grant_revision` 不可变审批前置事实为唯一口径。门户、审批和落地执行必须把当前授权列表返回的 `grant_id` 与 `grant_revision` 原样绑定到 `base_grant_id` 与 `base_grant_revision`，执行时不允许回退读取最新授权。后续若引入独立历史表，只能作为审计投影，不得再形成第二套授权版本语义。
5. 顶栏通知中心与门户安全设置在没有真实能力前删除入口。通知能力只保留已实现的 App 通知 API、投递状态与控制台通道配置；用户通知中心、未读数、已读状态和门户个人安全设置不在当前产品能力内。

## 后果

- 新建或重置本地管理员后，首次密码验证会进入 `/auth/local/security/` 绑定二次因子；完成绑定后才可进入 `/console/`。
- 只有 Django `_auth_user_id` 或 staff/superuser session 的请求无法进入 `/admin/`，因为路由不存在。
- 控制台 App 列表成为权限过滤后的工作目录，而不是组织级公开目录。
- 授权申请冲突统一表现为 `base_grant_revision_conflict` 或申请过期，不提供“使用最新授权继续”的兼容路径。
- 前端不展示没有数据源和写能力的通知/门户安全设置入口，避免用户把占位空态误认为可用功能。
