# 历史迁移的数据保护基线

## 背景

早期有几条迁移会无条件删除、清空或静默改写业务事实。项目虽未上线，但本地开发库、Docker 库和
试点快照仍可能包含需要保留的业务事实或凭据——"未上线"不等于可以静默丢数据。

这些迁移现在都改成了 **fail-fast**：只在可证明安全的历史状态下继续执行，否则在任何破坏性
schema 或数据变更**之前**失败，并输出行数和最多 5 个样本主键（错误消息不含 secret 明文）。

## 阻断条件与处置

| 迁移 | 阻断条件 | 操作员处置 |
| --- | --- | --- |
| `access_requests.0009` 申请幂等 | 旧申请表非空 | 导出申请、审批人和目标权限/授权组，按当前幂等契约显式重建或人工关闭，再重新迁移。迁移不能凭空生成 `idempotency_key` 和 `payload_digest`。 |
| `applications.0012` 审批规则唯一 | 同一目标存在重复规则 | 人工合并重复规则、明确保留的审批人集合和审计说明。迁移不能按最大 id 保留一条并删除其余。 |
| `grants.0005` 成员期限 | 旧授权表非空 | 导出授权、成员权限和授权组，按当前成员级期限契约显式重建。父级 `grant_type` / `grant_expires_at` 不能静默投射到成员级。 |
| `grants.0003` 授权版本唯一 | `(user, app, version)` 重复 | 人工确定真实版本序列。版本是审批和授权事实的一部分，迁移不能重编号。 |
| `accounts.0007` TOTP 加密 | 存在本地管理员 TOTP 种子 | 通知管理员重新绑定二次验证，迁移前显式清除旧明文种子并记录处置。 |
| `accounts.0013` 目录状态 | 状态不在 `active/disabled/departed` | 回到目录同步事实修正状态来源，不得把未知状态降级为禁用。 |
| `applications.0015` Authentik token 加密 | 存在明文 `authentik_api_token` | 通过运维流程重新录入凭据，迁移前显式清除旧明文并记录处置。 |
| `applications.0025` 凭据能力 | 已启用 App capability 且该 App 仍有 active 凭据 | 由 App owner 对每条凭据显式授权 capability。迁移不代替授权决策。 |

失败后原始行仍保留在失败前的 schema 中，由操作员用独立、显式、可审计的流程处置。

## 其余迁移的写入是安全的

复查全部迁移中的 `.delete()`、`.update()`、`bulk_create()`、`get_or_create()` 和
`update_or_create()` 后，剩余写入属于确定性结构迁移或已有 fail-fast 保护：

- 角色到授权组、申请审批人关系等 `bulk_create()` 是从旧字段到新关系表的确定性复制，缺目标行
  时失败，不会删旧事实再猜。
- 通知通道历史绑定只在目录作用域唯一或通道完整时执行，否则失败。逆迁移只处理迁移自己创建的
  通道，不作为升级路径的数据清理手段（`applications.0027` 同理）。
- 目录身份绑定形状、托管范围策略、跨 App 关系和状态机迁移都有只读扫描，坏数据时失败。

## 验收要求

- 空库 SQLite 完整迁移必须通过。
- PostgreSQL 16 lane 必须执行同一空库完整迁移回放。
- 携带旧快照升级时，不允许出现破坏业务事实的 `delete()`、批量 `update(secret="")`、默认值回
  填、自动重编号、未知状态降级、自动凭据授权或读取时兼容转换。

回归测试见 `tests/integration/migrations/test_historical_destructive_migrations.py`。
