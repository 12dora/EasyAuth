**a725acff breaks BE-P3-02: re-deleting an already-cancelled sample request now returns 404 instead of the contractual idempotent 204, and the branch that was supposed to preserve it is dead code.**

Evidence: delete_sample_request() now calls lock_sample_write_roots(db, request_id, allow_terminal_inquiry=True) (line 31) before the cancelled check (line 33). lock_sample_write_roots ends with `return inquiry, request_or_hidden_404(db, request_id, populate_existing=True)` (sample_requests_queries.py:130), and request_or_hidden_404 applies active_request_filter (sample_requests_queries.py:32-39), which filters `SampleRequest.cancelled_at IS NULL` AND `status != CANCELLED`. So for a cancelled request it raises HTTPException(404, "资源不存在或无权访问") and line 33's `if req.status == CANCELLED: return` can never be reached. Empirically confirmed inside the running backend container (seeded a CANCELLED SampleRequest in a rolled-back transaction and called lock_sample_write_roots): `RESULT: raised HTTPException 404 资源不存在或无权访问`. The old code returned 204 for exactly this case. No existing test covers it — app/tests/api/test_sample_requests.py, app/tests/test_sample_requests_api.py and 6 other targeted modules all pass (146 passed), so the regression is silent. The commit message claims "已取消幂等 204 在持锁复核后返回", which is not what the code does. Secondary loss: for a cancelled request whose parent inquiry was soft-deleted, the old path also returned 204; now 404. Fix: read the request status under the lock without the active filter (e.g. use the row returned by lock_sample_request_for_update, or add an allow_cancelled flag to lock_sample_write_roots) before applying active_request_filter.

The same race means test_pg_activity_update_/order_write_/sample_delete_ (lines 265, 292, 321) can pass with A already rolled back before B takes its first lock, i.e. proving nothing — the exact '假绿(两事务根本没争锁)' the original f76608ca docstring said the control case existed to prevent.
