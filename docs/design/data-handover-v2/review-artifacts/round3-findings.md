### [a1c-endpoints-01] BLOCKER (confirmed) async-abandon endpoint always 500s: LeaseHandle built with non-existent keyword arguments

- **File**: `src/easyauth/lifecycle/handover.py:897`
- **Description**: `LeaseHandle` (src/easyauth/lifecycle/lease.py:30) is `@dataclass(frozen=True, slots=True)` with exactly the fields `lease_id, owner, fence, expires_at`. `async_abandon_action()` constructs it twice with a completely different keyword set: `LeaseHandle(subject_user_id=..., app_id=..., fence=..., owner=...)` at handover.py:897 and again at handover.py:1026. Both raise `TypeError: LeaseHandle.__init__() got an unexpected keyword argument 'subject_user_id'` (verified by reproducing the dataclass signature). Failure scenario: an action reaches `async_attention_required` (poll attempts exhausted); a superuser opens the console action panel and clicks the async-abandon dialog with `{"outcome":"done"|"failed","reason":"<>=10 chars>","summary":null}` -> POST /console/api/v1/lifecycle/handover-tasks/{id}/actions/{app_key}/async-abandon. `console_handover_async_abandon` only catches `(HandoverConflictError, HandoverError)`, so the TypeError escapes as HTTP 500 before any state is written. This violates 01 §6.3, which makes this endpoint the *only* exit from `async_attention_required` ('没有这个端点，async_attention_required 就是个没有任何出口的终点… (subject, app) 永久锁死'): the lease is never released, the action cannot be retried (not `failed`), cannot be skipped (lease held), and no beat advances it — the (subject, app) pair is permanently locked exactly as the doc warns. There is no test exercising this endpoint (`grep async_abandon tests/` returns nothing).
- **Suggested fix**: Build the handle the same way `poll_async_action` does: `LeaseHandle(lease_id=int(lease.pk), owner=lease.owner, fence=int(lease.fence), expires_at=lease.lease_expires_at)` at both sites (handover.py:897 and :1026), and add an integration test that drives an action into `async_attention_required` and asserts async-abandon returns 200 with the lease released for both `done` and `failed`.

### [a1c-endpoints-02] BLOCKER (confirmed) items endpoints never emit `snapshot_stale` (412) or `downstream_locked` (423) — frontend branches are dead

- **File**: `src/easyauth/portal/handover_api.py:351`
- **Description**: 01 §6.1 freezes `412 CONFLICT / details.reason=snapshot_stale` and `423 CONFLICT / details.reason=downstream_locked`, and its callout says explicitly '前端只需要知道：execute 或 **items** 返回 412 snapshot_stale 时，要清掉本地状态并引导用户重新 preview'. 03 §3.5 line 278 mandates that the downstream `items` handler returns 412 on stale token. `fetch_action_items` calls `signed_hook_post`, and `_parse_hook_response` (webhooks/hooks.py:134) raises `HookCallError('应用交接接口返回 HTTP 412。', status_code=412)` for any non-2xx. `portal_handover_items` catches `(HandoverConflictError, HandoverError, HookCallError)` and calls `map_handover_exception`, which returns None for HookCallError (it only handles the two Handover* types), so the handler falls through to `error_response(VALIDATION_ERROR, str(error), {'reason': str(error)}, status=400)`. Failure scenario: user opens the item drawer for a type after data changed downstream; EasyTrade answers 412; the browser receives `400 {"error":{"code":"VALIDATION_ERROR","details":{"reason":"应用交接接口返回 HTTP 412。"}}}`. `apiErrorReason()` returns that Chinese sentence, so AssetAllocator.tsx:376 (`if (reason === 'snapshot_stale')`) and :384 (`downstream_locked`) never fire — the local override drafts are NOT cleared, `onSnapshotStale` never bubbles up, and the user keeps editing a stale list; only a raw error string is shown. The execute/preview/retry handler (portal_handover_api.py:564-576) does implement the `'412' in text` mapping, so the asymmetry is clearly an omission. `console_handover_items` (admin_console/handover_v2_api.py:580) has the identical gap.
- **Suggested fix**: Extract the 412/413/423 status mapping used in `portal_handover_action_operation` into a shared helper keyed on `HookCallError.status_code` (not on substring matching), and apply it in both `portal_handover_items` and `console_handover_items`. Add a test that stubs the items hook to return 412 and asserts HTTP 412 with `details.reason == 'snapshot_stale'`.

### [a1c-endpoints-03] MAJOR (confirmed) §6.2 `summary` is always an empty object — the redactor strips the per-type counter dicts

- **File**: `src/easyauth/lifecycle/api_payloads.py:291`
- **Description**: `aggregated_summary()` reconstructs `action.summary` from `HandoverDeliveryAttempt.response_payload`, but that column is written through `_redact_response_payload()` (handover.py:2092), whose whitelist keeps only scalar values: `{k: v for k, v in payload['summary'].items() if isinstance(v, int|float|str|bool) ...}`. The v2 summary shape is `{type_key: {transferred, released, skipped, merged, failed}}` (00 §10.5) — every value is a dict, so the whitelist drops all of them and the stored payload is `{'sha256':…, 'byte_length':…, 'summary': {}}` (verified by simulation). Back in `aggregated_summary`, `payload.get('summary')` returns `{}`, `isinstance({}, dict)` is True, so `found = True`, the loop body never runs, and the function returns `{}` — the `if not found: return action.result_summary` fallback (which holds the correct merged data written by `_merge_result_summary`) is unreachable. Failure scenario: an offboard action completes successfully with `{"customer":{"transferred":185,"released":1,"skipped":1,"merged":0,"failed":0}}`; GET /portal/api/v1/handover-tasks/{id} returns `"summary": {}` for that action. `HandoverActionPanel.tsx:315` tests `status === 'done' && action.summary` — `{}` is truthy in JS — so it renders the result panel with `Object.entries({})`, i.e. an empty result table. The user is told the handover finished but is shown zero transferred/released/skipped counts, contradicting §6.2 and the 'execute 成功后（含 summary 摘要）' audit requirement in §6.4.
- **Suggested fix**: Either make `_redact_response_payload` keep the five frozen integer fields of each per-type dict (the counters are not sensitive), or — simpler and closer to the doc — have `aggregated_summary()` return `action.result_summary` directly (it is already the correct '各批 summary 逐字段相加' value per 00 §10.5) and drop the delivery-attempt reconstruction. Add an assertion on the `summary` field to the existing execute test in tests/unit/lifecycle/test_services.py.

### [a1c-endpoints-04] MAJOR (confirmed) Duplicate pre-offboard returns 200 with the existing task instead of 409 `open_task_exists`

- **File**: `src/easyauth/lifecycle/offboarding.py:143`
- **Description**: 01 §6.1 makes the precondition for POST /portal/api/v1/handover-tasks/pre-offboard '自己无 open 的 offboard/transfer/pre_offboard 单', and the frozen error table row is `409 | CONFLICT | open_task_exists | 自助建单时已有 open 的 offboard/transfer/pre_offboard 单`. In `ensure_handover_task`, when an open lifecycle task already exists and its kind equals the requested kind, the code returns `(existing, False)` (offboarding.py:143) instead of raising; only the *different*-kind case raises `TASK_KIND_CONFLICT_MESSAGE`. `portal_handover_pre_offboard` then returns `HTTPStatus.OK` because `created` is False (handover_api.py:215). Failure scenario: an employee opens the 提前交接 dialog, creates a pre_offboard task, closes it, reopens the dialog (which mints a *fresh* `crypto.randomUUID()` idempotency key at PortalPreOffboardDialog.tsx:17, so the idempotency short-circuit does not apply) and clicks confirm — the backend answers 200 and the dialog's `onSuccess` silently navigates to the old task. The `open_task_exists` branch at PortalPreOffboardDialog.tsx:35 (which is supposed to show the amber '已有进行中的单据' banner plus a 'go to existing' link) is dead code and is never exercised. Note this is only correct today by accident for the cross-kind case (existing transfer/offboard), which does raise.
- **Suggested fix**: In the same-kind branch, distinguish the two callers: keep the idempotent return for internal/system callers, but for the portal self-service path raise `HandoverConflictError('open_task_exists')` (e.g. via a `raise_on_existing=True` kwarg) so `portal_handover_pre_offboard` yields 409 + `details.reason='open_task_exists'`. Optionally include `details.task_id` — the frontend already reads it at PortalPreOffboardDialog.tsx:37-40.

### [a1c-endpoints-05] MAJOR (confirmed) retry on a non-`failed` action emits `action_not_operable` instead of the frozen `action_not_retryable`

- **File**: `src/easyauth/lifecycle/handover.py:232`
- **Description**: 01 §6.1 freezes two rows for retry: the endpoint row ('仅 `failed` 可重试，否则 `409 action_not_retryable`') and the error-table row ('409 | CONFLICT | `action_not_retryable` | 对非 `failed` 状态的 action 调 `retry`'). `retry_action()` delegates to `_execute_action(allowed_status=ACTION_STATUS_FAILED, ...)`, whose first guard is `ensure_action_status(action, allowed={ACTION_STATUS_FAILED})` (core.py:80-83), which raises `HandoverConflictError(ACTION_NOT_OPERABLE_MESSAGE)` — the Chinese string '该应用交接动作当前状态不允许执行此操作。'. `map_handover_exception` does not find that text in `_REASON_TABLE`, so it falls to `reason_error('action_not_operable', text)`. Failure scenario: two tabs are open on the same action; tab A clicks 重试 and succeeds (action -> done); tab B, still showing the stale `failed` state, clicks 重试 -> the response is `409 {"details":{"reason":"action_not_operable"}}`, not `action_not_retryable`. `action_not_retryable` is in fact only raised at handover.py:1193 (retry when no FAILED batch row exists), i.e. the *documented primary* trigger never produces the documented string. A frontend that branches on `action_not_retryable` (the reason is present in api_errors.py precisely because §6.1 mandates it) can never match.
- **Suggested fix**: In `_execute_action`, when `is_retry` is True and the status guard fails, raise `HandoverConflictError('action_not_retryable')` instead of relying on the generic `ensure_action_status` message — e.g. check `action.status != ACTION_STATUS_FAILED` explicitly before calling `ensure_action_status` in the retry path.

### [a1c-endpoints-06] MAJOR (confirmed) `escalation.defer_history` is hard-coded to `[]`, so the deferral responsibility chain is never shown

- **File**: `src/easyauth/lifecycle/api_payloads.py:72`
- **Description**: 01 §6.2 specifies `escalation.defer_history` as `[{escalation_level, actor_id, at, reason}]`, '由审计事件生成, 永久保留', and §6.3's `escalation/defer` row requires '单据上永久显示「已由 {超管} 于 {时间} 顺延：{理由}」'. `escalation_payload()` returns `"defer_history": []` unconditionally, for both the list and the detail response (the comment '列表端点不强制扫审计' concedes only the list case, but the same function backs `task_detail`). `console_handover_defer` does write the `handover_task_deferred` audit row with the reason, so the data exists — it is simply never read back. ### [a1c-endpoints-07] MAJOR (confirmed) Console `handover-capability/sync` never re-fetches the descriptor; it fabricates the manifest from local DB state

- **File**: `src/easyauth/admin_console/handover_v2_api.py:822`
- **Description**: 01 §6.3 defines POST `.../apps/{app_key}/handover-capability/sync` as '手动触发 §5.2 descriptor 同步', and §5.2 is explicit: '控制台的「重新同步」按钮走既有的 manifest 重新拉取路径（那条路径本来就有 base_url 与凭证），**不另造一条**'. The implementation builds a throw-away `_Lifecycle` object out of purely local data — `capabilities = ('handover.v2',) if config and config.handover_url else ()`, `handover_url = config.handover_url`, `handover_asset_types = app.handover_asset_types` (i.e. the app's own already-stored value fed back into itself) — and hands that to `sync_handover_capability_from_manifest`. No HTTP call to `/.well-known/easyauth-app.json` is made; the existing pull path (`sync_app_manifest`, used at admin_console/auto_onboarding_api.py:134) is not reused. Two concrete failures: (a) EasyProject adds `handover.v2` plus three new `handover_asset_types` to its manifest; an operator clicks 重新同步 — `handover_asset_types` is written back unchanged (self-assignment), `handover_capability_synced_at` is bumped, and the console reports success while the new asset types are never picked up, so preview keeps seeding the old placeholder set. (b) An app whose manifest has *no* `handover.v2` capability but which has a leftover `AppWebhookConfig.handover_url` row is flipped from `undeclared` to `declared` by the sync button alone, and `reconcile_blocked_actions` then un-blocks every open blocked action for it — execute will subsequently fail against an app that never declared the capability, violating the §9.1 three-state table.
- **Suggested fix**: Make the endpoint re-run the real manifest pull (the same code path as auto_onboarding_api's resync, which has base_url + credentials) and pass the parsed `AppManifestLifecycleInput` into `sync_handover_capability_from_manifest`; if the app has no configured base_url, return an explicit error rather than synthesizing capabilities from `AppWebhookConfig.handover_url`.

## 分片 a1c-reassign-adr36（EasyAuth A1c）— 8 条 (blocker 1 / major 4 / minor 3)

### [a1c-reassign-adr36-01] BLOCKER (confirmed) A single non-active co-approver makes approval reassignment abort offboarding task creation and the entire directory-sync run

- **File**: `src/easyauth/lifecycle/approvals.py:94`
- **Description**: reassign_access_request_approvers() builds `desired` from the request's existing approvers minus the departing user and passes the whole set to reassign_access_request(). That function validates that EVERY id in the list is `status=active` (access_requests/approvals.py:334-348, REASSIGN_APPROVER_INVALID_MESSAGE) and raises ApprovalActionError otherwise. §4.5.1 requires keeping the surviving approvers (the doc's own example is `[离职主管, 财务]`), but nothing filters them for activity, and nothing catches the exception. reassign_approvals_for_departed() runs inside ensure_handover_task()'s transaction.atomic() (lifecycle/offboarding.py:206-212, and again on upgrade at :294), so the error rolls back the whole handover task, and it propagates further out of start_offboarding() into the un-guarded directory-sync loop (integrations/authentik/directory_sync.py:637), aborting the batch. Concrete failure (verified by running a probe test): submitted AccessRequest with approvers [departed_user, finance] where `finance.status == 'disabled'` (or a user who departed before this feature shipped, i.e. exactly the data §4.5.1 exists to clean up); departing user's offboarding → `ApprovalActionError: 审批人必须是在职人员。` raised from approvals.py:94 → no HandoverTask is created even though apply_directory_status() already committed the departure and revoked grants, and every user later in the sync batch is left unprocessed. The same abort happens if a concurrent approve/reject flips the request out of `submitted` between the unlocked read at approvals.py:75-80 and the locked status re-check inside reassign_access_request() (kind='conflict'). This violates §4.5 ('离职建单同事务内执行') and 铁律一 (a departure must always produce a handover task).
- **Suggested fix**: Filter `desired` down to active, non-local-admin UserMirrors before calling reassign_access_request() (falling through to the superuser_pool branch when the filtered set is empty), and wrap each per-request reassignment in try/except ApprovalActionError so that one un-reassignable request can never roll back 建单 — log/audit the failure instead (e.g. leave the request in superuser_pool).

### [a1c-reassign-adr36-02] MAJOR (confirmed) Departing user is re-instated as approver when their mirror is still active; audit reports a reassignment that did not happen

- **File**: `src/easyauth/lifecycle/approvals.py:83`
- **Description**: The candidate returned by resolve_assignee(access_request.user) is only rejected when it equals the applicant (approvals.py:87-91); there is no check that it is the departing subject. resolve_assignee() only filters on `status != active`, so as long as the subject's mirror is still `active` the subject is returned as the applicant's own manager and appended straight back into `desired`. ### [a1c-beat-upgrade-conservation-01] BLOCKER (confirmed) Conservation-failure state (failed status + lease release) is rolled back by raising inside the atomic block

- **File**: `src/easyauth/lifecycle/handover.py:407-423`
- **Description**: In `complete_data_phase` transaction A, when `validate_execute_summary_conservation()` returns an error the code sets `action.status=failed`, `last_error`, `batch.status=failed`, calls `must_cas_release(handle)` and `refresh_task_status_locked()` — and then does `raise HandoverError("summary_conservation_failed")` **while still inside `with transaction.atomic():`**. The exception propagates out of the atomic block, so Django rolls the whole transaction back: none of those writes survive. Compare the sibling grant-transfer failure path at lines 466-486, which deliberately stashes `grant_error` and raises *after* the block exactly to avoid this. Failure scenario: EasyTrade returns 200 with `summary.customer = {transferred:5,...}` while the batch's preview `count` was 10 (a real conservation break — data has already been rewritten downstream). EasyAuth rolls everything back, so the action stays `executing`, the batch stays `executing`, and the lease row keeps `released_at IS NULL`. The API returns 500/409 with no persisted failure. - **Suggested fix**: Mirror the transaction-B pattern: record the conservation error into a local variable, let the atomic block exit normally so the `failed` marking, batch status and `must_cas_release` commit, then `raise HandoverError("summary_conservation_failed")` outside the `with` block.
